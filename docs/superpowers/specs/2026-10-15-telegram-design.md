# Telegram integration — approved design

The user approved implementation on 2026-10-15 and then explicitly changed hosting: AI and Telegram run on this Windows PC with VPN, PostgreSQL and RabbitMQ remain on the VPS. Add `stoq-telegram-service` as an independent NestJS service. Do not edit README files or change existing RabbitMQ infrastructure, RPC envelopes, exchanges, or queues. Use the existing CommandBusService/RabbitRPC/executeRpc patterns. A dedicated Telegram event subscription to existing event routing keys is authorized by the approved design.

## User flows

Private Telegram chats only. `/start` offers login by existing email/password; password input is removed immediately and never persisted or logged. Login attempts are rate limited. Only unblocked ADMIN/MANAGER users qualify. Auth issues a separate opaque, expiring Telegram session bound to Telegram user ID; web refresh tokens are untouched. The auth database stores only a session digest. The bot encrypts its session credential at rest using an environment key. Verify session, current role, tenant, blocked state and tokenVersion before commands and each outgoing business message. `/logout` revokes only the Telegram session and clears pending messages and secrets. No data is sent to groups or an unverified chat.

Persistent menu: summary now, notifications, daily summary, logout. Notification switches: supplies/stock changes, manual writeoff/inventory adjustments, automatic expiry, dish shortage/stop-list/recovery. Preferences survive restarts. Stop-list snapshots produce notifications for changes only, with an initial baseline rather than replaying all current problems.

Summary now covers today's Moscow business date and current inventory; scheduled daily summary covers the previous complete Moscow date. Default schedule 09:00 Europe/Moscow, configurable HH:mm and opt-in. Summary uses existing backend statistics, not invented values: revenue, estimated ingredient-cost profit (clearly named, unknown values remain unknown), orders/completed/average check, active/low/stop dishes, products running low, upcoming expiry and expired batches awaiting disposal. Extend existing period aggregation only as needed for an exact daily summary; keep existing 7/14/30-day contracts stable.

## Reliability and boundaries

Use Telegram Bot API long polling (no public inbound bot port); validate private message sender/chat identity and callback identity. Persist safe update offset; transient password conversation state remains memory-only with expiry. Persist an outbox and source identities for event deduplication and scheduled-day uniqueness. Retry Telegram 429 according to retry_after; back off network/5xx failures; blocked chats stop delivery. Persist before acknowledging business events. Avoid claiming exactly-once delivery across ambiguous Telegram network outcomes. Coalesce noisy stock/stop-list events and bound payloads to Telegram limits. Persist queued business message intents, verify authorization at delivery, and expire stale intents. Never log token-bearing URLs, credentials, raw Telegram updates or financial message bodies.

The service owns a PostgreSQL database for subscriptions/preferences/update cursor/outbox/status snapshots. Auth owns Telegram sessions. Existing business commands are invoked within verified restaurant context. Existing publishers and websocket gateways are preserved. A dedicated durable Telegram consumer gets its own copy of stock.changed, batch_expired and stop_list.updated events; do not consume from existing consumers' queues. No universal message transport abstraction.

## Operations and acceptance

A common local launcher maintains one restricted SSH connection for local broker port15674 and PostgreSQL port15432 and starts both workers, recovering after failures. Server workers are disabled by systemd conditions to avoid competing consumers. Local runtime and key have restricted Windows ACLs; startup follows existing Windows user autostart. Without a bot token the service reports waiting configuration and does not poll Telegram; unrelated services remain healthy. Configure actual token only once provided by user. Test role/tenant/chat isolation, separate-session behavior, password erasure, preference persistence, daily date boundaries, event deduplication/status transitions, retries and disabled delivery. Run CI migrations on empty PostgreSQL databases as the app role and production health checks. Preserve Redis/RabbitMQ behavior. No Telegram message to any user until they explicitly start/login to this bot.
