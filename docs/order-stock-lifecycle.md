# Списание продуктов по заказу

Создание заказа с блюдами выполняется по схеме `pending_reservation` → списание
продуктов → `created` («В обработке» в интерфейсе). Используется существующая
команда `DEDUCT_STOCK_INVENTORY` с ключом `order-{id}-deduction`. Рецептура
разрешается один раз при создании; те же количества используются для проверки
и списания. Завершение (`completed`) повторно продукты не списывает.

Запросы создания одного ресторана обрабатываются в порядке поступления в
единственный экземпляр сервиса заказов, включая время получения рецептур.
Клиентская дата заказа не определяет приоритет. При нескольких экземплярах
сервиса общей гарантии FIFO нет; атомарная проверка остатка на складе сохраняет
защиту от двойного списания последней порции.

На складе ключ идемпотентности, движения и изменения остатков сохраняются в одной
транзакции. Изменение каждого остатка проверяет прочитанное значение; конфликт
откатывает всю транзакцию, включая уже обработанные ингредиенты.

`PATCH /orders/{id}/status` принимает `completed` и `rejected`. Отклонение убирает
заказ из активного списка. Уже списанные продукты автоматически не возвращаются:
это списание при начале обработки, а отдельной команды возврата в текущем
контракте нет. Закрытые и отменённые заказы повторно менять нельзя.

После создания состав заказа зафиксирован; добавление позиций возвращает `409`.
Все блюда следует передавать в первоначальном запросе создания заказа. Это
предотвращает появление позиций без соответствующего списания продуктов.

Если склад вернул окончательный отказ (`4xx`), созданный технический заказ
переходит в `rejected`. Если ответ потерян или получена серверная ошибка, заказ
остаётся `pending_reservation`: списание могло успеть зафиксироваться. Такой заказ
нельзя завершить, отклонить или удалить до сверки со складом. Автоматическое
восстановление после сбоя между сервисами не добавлено; требуется сверка ключа
идемпотентности и движений этого заказа. Миграции схемы и изменения RabbitMQ
для этого поведения не требуются.
