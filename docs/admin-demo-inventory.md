# Админка, тестовый ресторан и склад

Обновлять нужно `stoq-auth-service` и `stoq-gate`. Существующие exchanges,
очереди, CommandBusService и формат RPC сохранены. Новые операции auth используют
тот же RabbitRPC/executeRpc и очередь auth.commands.

## Обновление базы auth

Перед запуском обновлённого auth применить миграцию
`20261015170000_admin_invitations_demo` и сгенерировать Prisma client:

```powershell
cd backend/stoq-auth-service
npx prisma migrate deploy
npx prisma generate
```

Команды используют `DATABASE_URL` из окружения этого сервиса. Миграция добавляет
блокировку пользователя, признаки демо-ресторана и его готовности, таблицу
приглашений. Для существующих записей новые признаки имеют значение `false`.
Миграции рабочих данных склада/каталога/заказов эта задача не добавляет.

## HTTP API

- Публичный `GET /restaurants` возвращает список для регистрации.
- `GET /auth/admin/users` возвращает сотрудников только ресторана администратора.
- `PATCH /auth/admin/users/:id/role` принимает `{ role }`.
- `PATCH /auth/admin/users/:id/block` принимает `{ blocked }` и отзывает сессии.
- `GET/PATCH /auth/admin/restaurant` читает/обновляет текущий ресторан.
- `GET/POST /auth/admin/invitations`: создание принимает `{ role, hours }`.
- `PATCH /auth/admin/invitations/:id/revoke`, `DELETE /auth/admin/invitations/:id`.
- Регистрация сотрудника принимает необязательный `invitationId`. Ссылка
  одноразовая: проверяются ресторан, срок, отзыв и использование. Без приглашения
  сотрудник ожидает подтверждения администратора.

## Тестовый ресторан

`POST /test/restaurant` доступен администратору. Создаёт отдельный ресторан,
четыре аккаунта (ADMIN, MANAGER, WAITER, STOREKEEPER), единицы, шесть продуктов,
три блюда с рецептами, принятую поставку, поставку в пути и заказ. Все бизнес-
команды выполняются в контексте нового restaurantId. Текущий ресторан не меняется.

Готовность отмечается только после успешного заполнения. При ошибке API сообщает
ID незавершённого ресторана; он не появляется в списке тестового входа.
`GET /test/restaurants` возвращает готовые демо-рестораны и безопасные описания
аккаунтов. `POST /test/restaurants/:id/login` с `{ role }` устанавливает обычные
auth-cookies. Пароли и JWT не возвращаются в JSON интерфейсу. На production демо-
рестораны разрешает `ENABLE_DEMO_RESTAURANTS=true` в gateway и auth. Сброс данных
управляется отдельным `ENABLE_TEST_TOOLS`, который остаётся выключенным.

## Склад и гостевые заказы

Чтение склада на фронте выполняется только через Socket.IO namespace `/inventory`.
`inventory:getStock` с `{ requestId: 'store' }` возвращает полный склад через
существующую команду GET_INVENTORY; переданный `productIds` продолжает работать
через GET_INVENTORY_STOCK. Для срока годности используется
`inventory:getExpiringSoon`. HTTP PUT инвентаризации и POST списания сохранены.
Первоначальный снимок не создаёт уведомлений. Из пары событий списания по сроку
годности уведомление показывает подробное событие `inventory:batchExpired`.

Публичные `GET /menu` и `POST /orders` требуют `X-Restaurant-Id` выбранного
ресторана. Фронт передаёт его из гостевой ссылки и не отправляет cookies
сотрудника; меню, корзина и квитанция изолированы по ресторану.
